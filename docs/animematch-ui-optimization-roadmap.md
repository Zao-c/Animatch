# AniMatch UI 简化与二次元化路线

这份文档是 AniMatch 后续 UI 优化的约束文件。它不改变运行时代码、API、数据库或路由，只定义后续界面改造必须遵守的视觉方向、信息层级、组件使用和验收标准。

当前核心判断：AniMatch 已经不再是纯 demo，但界面仍显得繁杂。繁杂感主要来自同屏同时展示说明卡、统计卡、操作按钮、管理控件和高级功能。下一轮优化应先做信息减法，再做二次元氛围增强。

目标体验：

> 用左右选择完成两两对决，生成自己的动画 Tier List。

## 1. Design North Star

AniMatch 应该像一个清爽的番剧对决场，而不是一个数据库管理后台。

设计关键词：

- 二次元，但不堆装饰。
- 简洁，不是空。
- 轻竞技，不是企业 dashboard。
- 封面优先，因为动画作品靠视觉记忆被识别。
- 主动作优先，每个页面只突出一个最重要的下一步。
- 复杂能力渐进展开，不在首屏一次性暴露。

风格基调：

- 清爽番剧竞技场。
- 深色底可以保留，但要减少“全黑 + 青色按钮”的单一感。
- 用少量粉、紫、金、蓝、绿做情绪、Tier 和状态识别。
- 动画封面、对决状态、榜单结果应成为页面主角。
- 二次元感优先来自真实封面、榜单色块、轻竞技交互和文案气质，而不是更多贴纸、霓虹和背景装饰。

明确避免：

- 通用 SaaS 后台布局。
- 等权重卡片堆满页面。
- 所有按钮和高亮都使用同一种青色。
- 霓虹、渐变、发光过多，压过动画封面。
- 搜索、导入、编辑、校准等管理工具全部外露。

## 2. 减法优先原则

后续 UI 改造的第一原则是删减信息层级，而不是增加视觉元素。

- 每个页面只允许一个最明显的主动作。
- 说明卡默认折叠，除非它直接决定用户下一步。
- 同屏不要同时展示大统计、长说明、管理操作和高级操作。
- 卡片数量和边框数量要克制；能用留白和分组表达的，不再加一层卡片。
- 顶部区域只回答三个问题：我在哪里、当前状态是什么、下一步做什么。
- 高级操作必须收进菜单、抽屉、折叠区或独立任务面板。
- 右侧任务面板同一时间只展示一个任务，例如添加动画、编辑显示、导入模板不能并行抢注意力。
- 青色只用于主 CTA；粉、紫、金用于情绪高光、胜利反馈、Tier 和导出/分享。

繁杂来源诊断：

- 卡片容器过多：页面上几乎每段内容都被框起来，视觉噪声上升。
- 按钮同级过多：用户分不清哪个按钮是主路径。
- 文案解释过多：很多说明可以通过布局、状态和按钮文案表达。
- 数据指标过多：作品数、对决数、信心、阶段等指标同时展示会让页面像控制台。
- 管理控件外露过多：编辑、移除、归档、复制 ID、导入方式不应默认出现在主视图。

## 3. Non-negotiable UI Rules

- 用户进入任何页面后，3 秒内必须知道下一步该做什么。
- 番组 ready 时，“开始对决”是全站最重要的动作。
- 作品封面优先于文字说明；文字用于解释，封面负责吸引和识别。
- 归档、删除、移除等危险操作不能和主动作同级显示。
- 新 UI 必须优先使用 `AppButton`、`AppCard`、`AppBadge`、`PageShell`、`anime-field`。
- 不允许继续散落一次性的颜色、阴影、圆角和按钮 class；可复用状态必须沉淀为 token 或 variant。
- 移动端必须保证核心路径可用：创建番组、添加动画、开始对决、查看 Tier。
- 动效只服务于状态变化和反馈；必须尊重 `prefers-reduced-motion`。

## 4. Priority Roadmap

### P0: 先降噪

优先处理已经显得繁杂的区域：

- 首页删除底部两张说明卡，只保留 hero、mini match demo 和三步流程。
- 番组列表顶部大统计卡压缩为一行小状态。
- 番组卡默认只保留一个主按钮，其余操作收进低强调区或更多菜单。
- Tier 页折叠“榜单说明”“初始估计”“高级控制”。
- 作品墙默认隐藏“编辑显示 / 移除”，只在 hover、选中或更多菜单中出现。
- 右侧任务面板互斥：编辑显示时不同时展示添加动画面板。

### P0: 建立视觉系统边界

设计 token 和组件约束仍然重要，但不应让 token 变成更多装饰的理由。

建议 Tailwind token 家族：

- `anime.bg`：应用深色背景。
- `anime.panel`：标准面板。
- `anime.panelStrong`：弹窗、抽屉或聚焦区域。
- `anime.cyan`：主动作。
- `anime.pink`：二次元强调色、S Tier、胜利反馈。
- `anime.purple`：次级动作、A Tier、对决氛围。
- `anime.amber`：奖励、导出、分享。
- `anime.danger`：危险操作。
- `anime.muted`：低强调边框和文字。

组件规则：

- `AppButton` 统一按钮尺寸、variant、disabled、cursor、active feedback。
- `AppCard` 统一面板圆角、边框、模糊和阴影，但不要滥用成“所有东西都套卡片”。
- `AppBadge` 统一状态、来源、Tier、warning、muted、danger chip；同一卡片默认不超过 3 个 badge。
- `anime-field` 统一 input、textarea、select。
- 页面实现不要再直接写 `bg-zinc-900`、自定义 glow shadow 或临时 border color，除非这些样式被收敛到共享组件。

### P1: 二次元化但不加噪

二次元感不靠继续加贴纸和背景，而靠这些低噪声手段：

- mini match demo、作品墙、Tier 卡都优先使用真实封面。
- Logo 从单字母 `A` 逐步升级为徽章化标识，例如 Rank 徽章、对决牌、胶片牌。
- 背景网格弱化，避免工程感；可以保留非常轻的舞台光、星屑点阵或胶片颗粒。
- Tier 色块承担视觉情绪：S 粉金、A 紫、B 蓝、C 绿、D 灰绿。
- 文案保持 70% 清晰工具语言 + 30% 番剧氛围，避免满屏梗和过度中二。
- 动效用于对决选择、榜单拖拽、保存成功和导出反馈，不做持续装饰动效。

### P1: 页面级主路径

后续页面都按以下主路径收束：

- Home：理解产品并进入一次对决。
- Pools：快速找到一个番组并继续。
- New Pool：创建后立刻添加动画。
- Pool Detail：确认 ready 状态并开始对决。
- Add Anime：搜索或导入作品，不被导入方式淹没。
- Match：快速选择，不被指标干扰。
- Tier List：导出、分享、继续对决。

### P2: 响应式与可访问性 polish

- 深色背景上的重要辅助文字至少使用 `text-slate-400` 级别。
- 所有可点击控件必须有 pointer cursor、hover、focus-visible、disabled。
- 移动端 tap target 至少 44px 高。
- 文本不能溢出按钮、卡片或 badge。
- 不使用 viewport-based font scaling；使用固定响应式字号阶梯。
- 拖拽类交互需要可发现的状态和非拖拽 fallback。

## 5. Page-by-page Direction

### Home

目标：让新用户通过一个真实封面对决理解产品。

必须做到：

- 保留 hero + mini match demo + 三步流程。
- 删除底部两张说明卡，避免首页像产品说明文档。
- 三步流程从 4 步压缩为 3 步：添加动画、开始对决、生成榜单。
- mini match demo 必须使用真实封面、`VS` 和三个选择；不再使用渐变占位卡。
- 标题说明产品价值，而不只是展示品牌名。
- 长说明和 workflow 放到首屏之后，且默认不抢视觉主角。

### Pools

目标：让番组像活跃的动画集合，而不是控制台记录。

必须做到：

- 顶部大统计卡改成一行轻量状态，例如“4 个番组 / 1 个可开始 / 默认筛选全部”。
- 搜索和筛选保持，但不要占用过高视觉权重。
- 卡片结构统一为：封面条 + 标题 + 关键状态 + 一个主按钮 + 更多菜单。
- 卡片内三格指标默认不要强展示；可放在 hover、展开详情或小文本中。
- 每张卡只保留一个主按钮：`开始对决`、`继续对决` 或 `进入`。
- `添加动画`、`查看 Tier`、`编辑信息`、`复制 ID`、`归档番组` 收进低强调区或更多菜单。
- 危险操作只出现在更多菜单内，并保留确认流程。

### New Pool

目标：作为全站 onboarding 标准页。

必须做到：

- 保持表单在 `AppCard` 中，不回退到旧式裸表单。
- 主按钮固定为“创建并添加动画”。
- 示例 chips 可保留，但不超过 5 个。
- 右侧流程预览控制在 4 行以内，不再写长解释。
- 创建成功后进入添加动画位置。

### Pool Detail

目标：让用户准备开始对决，同时保留管理能力。

必须做到：

- 顶部只回答：有几部动画、是否 ready、下一步是什么。
- 作品墙是页面主角。
- 添加动画默认只展开搜索。
- 其他添加方式折叠到“更多导入方式”。
- 编辑显示使用右侧面板或 modal，但与添加动画面板互斥。
- 社区榜单、公开说明、权限说明等内容默认不要压在主工作区上方。

### Anime Wall

目标：让作品像番剧收藏墙，而不是管理列表。

必须做到：

- 默认展示封面、标题、少量 meta。
- `编辑显示 / 移除` 默认隐藏，只在 hover、选中或菜单中出现。
- `移除` 不直接暴露为常驻按钮。
- 长标题允许换行或合理截断，不能撑破卡片。
- 卡片下半部分文字对比度要足够，避免封面强、文字弱。

### Add Anime

目标：降低导入焦虑。

必须做到：

- 搜索优先。
- 标签、分类、Bangumi、TierMaker、手动添加、上传图片不能同时全展开。
- 每次只展开一个任务。
- 上传状态必须明确显示已选文件、错误和最终提交。
- 高级导入方式需要简短说明，但不要用大段文字抢主界面。

### Match

目标：让每次选择快速、有反馈。

必须做到：

- 封面更大。
- 默认少展示数学指标。
- 整卡可选。
- 支持键盘。
- 有 150-250ms 短反馈动效。
- 次要选择更低调。
- 错误提示不能破坏当前对决上下文。

### Tier List

目标：让榜单像可以导出分享的作品。

必须做到：

- 首屏只保留导出、分享、继续对决、核心进度。
- `榜单说明`、`初始估计`、`高级控制` 默认折叠。
- 系统说明和对决历史解释放入折叠说明，不常驻大卡片。
- Tier 行随内容收缩，减少右侧空白。
- 作品卡更像榜单贴纸：封面更大、文字更少、统计更弱。
- 强 Tier 标签保留，S/A/B/C/D 色块承担主要视觉识别。

### Global

必须做到：

- 背景网格弱化，减少工程感。
- 减少同屏卡片边框数量。
- 青色只用于主 CTA。
- 粉、紫、金用于情绪、对决、胜利、导出和 Tier 高光。
- 同一视图里的 badge 数量要克制；状态太多时改成摘要文本或折叠详情。

## 6. Component & Token Rules

后续 UI 工作可以新增或调整这些 UI 层接口：

- Tailwind theme extension：颜色、阴影、圆角、过渡时间。
- `AppButton` variants：`primary`、`secondary`、`ghost`、`danger`、`quiet`。
- `AppButton` sizes：`sm`、`md`、`lg`，必要时加 `icon`。
- `AppCard` variants：default panel、soft panel、focus panel、modal panel。
- `AppBadge` tones：source、status、tier、success、warning、danger、muted。
- 页面布局 helper：hero、toolbar、split panel、side drawer、mobile bottom nav。

约束：

- 一个页面首屏不应出现超过一个 focus panel。
- 一个卡片内默认不超过 3 个 badge。
- 一个任务区域默认不超过 2 个同级按钮；更多操作进菜单。
- 右侧任务面板必须互斥。
- `AppCard` 不是分隔所有内容的默认答案；能用间距和标题分组时优先不用卡。

Token 命名按用途，不按页面：

- 使用 `primary`、`accent`、`surface`、`surface-raised`、`border-muted`、`text-muted`。
- 不用某个页面名或一次性状态命名通用 token。

## 7. Motion, Accessibility, Responsive Checklist

动效：

- 动效用于选择、保存、提交、排序、打开、关闭。
- 常规过渡控制在 150-250ms。
- App shell 不做持续抢眼的装饰动效。
- 加复杂动效前，先加入全局 reduced-motion 规则：

```css
@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

可访问性：

- 保留 `:focus-visible`。
- label、helper text、disabled state 保持足够对比度。
- Tier、warning、destructive 状态不能只靠颜色表达。
- Match 需要键盘路径；Tier 拖拽需要替代操作或明确 fallback。
- icon-only 或 `...` 菜单必须有 `aria-label`。

响应式：

- 桌面 Match 可使用两列卡片 + 中间 `VS`。
- 移动端 Match 应堆叠卡片，或使用更适合滑动的一组对决布局。
- 添加面板在移动端变成 drawer 或全屏 sheet。
- Tier 行可以横向滚动，但左侧标签必须可读。
- 不允许页面级横向滚动。

## 8. Acceptance Criteria For Future UI Work

每次合并 UI 改动前检查：

- 页面只有一个最明显的主动作。
- 首屏没有同时出现大统计、长说明、管理操作和高级控制。
- 长动画标题不会撑破布局。
- 能用共享 UI primitive 的地方没有手写一次性 class。
- 没有新增无法复用的临时颜色或阴影。
- 危险操作低于导航和创建操作的视觉优先级。
- Match 可以用鼠标和键盘快速完成选择。
- 首页不被说明卡和营销文案占据。
- 需要识别作品时，动画封面足够可见。
- 移动端主流程可用，没有页面级横向溢出。
- reduced-motion 用户不会被迫观看非必要动画。
- 界面更二次元，但没有因为装饰增加噪声。

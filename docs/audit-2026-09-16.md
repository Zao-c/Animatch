# AniMatch 图片可靠性、工程问题与玩法建议

检查日期：2026-09-16。范围：当前 main、生产 Docker 部署、COS 配置、公开页面及浏览器榜单导出。没有对线上用户投票数据执行压力写入。

## 本次确认的原因与修复

| 问题 | 证据与影响 | 本次处理 |
| --- | --- | --- |
| COS 没有 CORS 规则 | 浏览器能展示封面，但 fetch 读取同一图片失败；存储桶返回空 CORSRules。显示成功不代表可导出。 | 为网站 `http://182.61.136.105:3000` 添加 GET/HEAD 跨域规则和 Vary；保留导出专用同源代理回退。 |
| 屏幕外图片被提前判失败 | 原 AnimeCover 挂载即开始 8 秒计时；导出容器在屏幕左侧 10000px 外，仍使用此懒加载组件。 | 进入视口附近才启动计时；慢图保持挂载以接受迟到的成功事件。导出使用独立、稳定的图片节点。 |
| 导出请求与组件状态互相干扰 | 旧导出直接改 React 管理的 img.src；组件可能同时移除或替换节点。线上临时补丁还会并发预热最多 80 张图。 | 在脱离 React 的克隆节点中读取图片，最多 4 个并发、相同 URL 合并、全局截止时间；嵌入后检查解码结果。 |
| 缺图被当作成功导出 | 读取失败被替换为透明占位图；固定两倍尺寸并关闭自动缩放，长榜单还可能超过 Canvas 能力。 | 未完成图片读取时明确报告数量并取消导出；限制输出边长及像素总量，校验 PNG 输出。没有原始封面的作品仍显示标题占位。 |
| 代理实际下载不受限制 | 收到响应头就释放并发名额、清除超时，正文下载另行读取；排队没有超时。 | 并发名额和超时覆盖完整正文；流式检查 10 MB 上限、限制排队时间、短暂记住失败，减少重复回源。 |
| 旧缓存仍等待原站 | 24 小时后的缓存先等待回源失败才回退；命中本地缓存前也要访问 DNS。 | 30 天以内的旧缓存立即响应，后台受控更新；已有缓存不依赖 DNS 可用性。 |
| COS 后台队列重复工作 | 项目刚出队就删除去重标记，仍在下载时可被下一位访问者重新加入。 | 下载及转存结束才解除标记；失败后短暂退避。 |
| 普通对决并发写入 | 普通对决使用数据库默认事务隔离；两个标签页可能从相同旧 Elo 计算并互相覆盖。 | 使用 Serializable 事务，并对写冲突、幂等键竞态做有限重试。赛季已有类似机制。 |
| 部署磁盘不足 | 生产磁盘使用 95%，仅约 4 GB 可用；构建缓存约 30 GB。 | 清理超过一周的未使用构建缓存，释放 20.61 GB；当时磁盘降到 70%，约 24 GB 可用。收紧 Docker 构建上下文，排除输出、缓存和本地文件。 |
| 本地合并冲突残留 | health、preload、测试和 README 有嵌套冲突标记。 | 原文件已备份到本地 backups/audit-20260916-original；恢复当前主分支的健康检查和预加载逻辑，清除冲突。 |

## 图片资源本身

最初 349 张在用封面中，322 张已转存 COS，27 张未转存。首次补缓存成功 25 张，其余两张的 MyAnimeList 原始地址返回 404。通过数据库保存的作品链接核对对应资料页后，找到两张新的 og:image 地址；修复只针对这两个确定的作品 ID，先备份旧字段。

当前使用的是 COS 公共对象地址，不能把它等同于已经接入自定义 CDN。现有规模下，先保证完整的 COS 覆盖、正确跨域、稳定导出和合理并发，比立即增加缓存中间件更有价值。

后续例行检查可运行：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml exec app pnpm covers:cache-cos --dry-run
docker compose --env-file .env.production -f docker-compose.prod.yml exec app pnpm covers:cache-cos --limit 100 --concurrency 2
```

第一条只统计；第二条补齐实际入池作品。不要为了预热而全量抓取整个动画库。公开分享快照可能保存旧图片地址，应另做一次历史分享抽查。

## 验证与适用范围

- 行为回归覆盖：正文下载挂起、无 Content-Length 的超大响应、完整下载并发限制、重复请求合并、失败退避、旧缓存即时响应、DNS 故障下缓存可用、跨域回退、缺图拒绝导出、整体超时和 Canvas 尺寸限制。
- 浏览器对照：视口外等待 9 秒，旧组件进入 error，新组件保持 loading；滚动后新组件成功 loaded。
- 浏览器生成了包含 58 个测试封面的完整 PNG，检查了全部行、封面和页脚。实际线上导出仍需随部署复核。
- 生产 CORS 修复前读取失败，修复后同一张图返回 HTTP 200、83,424 字节。
- 不将模拟并发测试等同于未知峰值流量下的容量保证。后续应记录封面失败率、缓存命中率、导出成功率及 P95 耗时。

## 尚需优先处理的工程问题

1. **账号身份验证，优先级最高。** `src/lib/auth-session.ts` 中，只要知道共享邀请码和用户名，就能取得该用户名的账号。公开展示用户名会增加冒用风险。建议为现有账号设计一次性认领流程，改为个人口令、邮箱验证码或 Passkey；邀请码只控制注册资格。此变更涉及现有用户身份迁移，本次没有直接替换登录方式。
2. **HTTPS 与入口。** 当前公网以 HTTP/IP:3000 提供服务。准备域名后在 Caddy/Nginx 终止 TLS，启用 Secure Cookie，并把应用端口限制到本机。CORS 同时补充实际 HTTPS 来源。
3. **大池配对成本。** `ranking-pairing.ts` 的候选枚举为 O(n²)，队列生成可能反复执行。先用 100/500/1000 部作品的真实数据测量，再改为按评分邻域、低比较次数和高不确定性抽取有限候选，保留探索比例及算法版本。
4. **数据库读取范围。** match/community 等路径多次加载完整 anime 记录和比较历史。逐步改成显式 select，避免带入 rawJson/长摘要；社区聚合优先在 SQL 完成，再按池版本缓存公开结果。用户私有结果必须保留用户和 run 维度。
5. **图片任务持久化。** 目前 COS 队列在进程内，重启会丢失待处理任务。下一步可用 PostgreSQL 的持久任务表记录状态、尝试次数和下次执行时间；导入时入队，工作进程受控消费。当前规模无需先引入 Redis 集群。
6. **前端职责和测试。** 池详情页很大，集中处理导入、管理、对决、社区和导出。按功能拆分并懒加载导入/导出模块。大量现有测试检查源码字符串，应逐步补上浏览器行为测试，尤其是慢网、手机、大榜单和并发点击。
7. **依赖升级。** 生产实际为 Next.js 14.2.35。将框架升级作为独立项目，依据当时官方支持和安全公告选择目标版本，在登录、路由和图片回归通过后部署；不要和图片故障修复混在一次大版本改造里。

## 玩法优先顺序

| 优先级 | 玩法 | 用户为什么愿意回来 | 最小版本与衡量方法 |
| --- | --- | --- | --- |
| 1 | 池内颁奖典礼 | 排完榜还有能表达观点、适合发群的结果 | 利用现有社区分歧、个人榜和赛季，先做最佳作品、最大分歧、个人遗珠三个奖；复用远端 feature/pool-awards 的产品方案，首版不同时铺开几十个奖项。看榜单完成后的分享率、分享访客参与率。 |
| 2 | 好友盲猜与口味对照 | 想知道朋友懂不懂自己，而不只是再排一次榜 | 公开分享的创建者主动开启挑战；朋友猜 Top 3/最喜欢的二选一，完成后显示共同偏好和最大分歧。共同看过的样本太少时不输出夸张相似度；保留退出选项。看邀请完成率。 |
| 3 | 每周 10 场主题挑战 | 每次只花几分钟，主题给用户明确入口 | 从既有池挑 12–20 部作品做固定场次短挑战，完成即产出小榜单；下一周换年代、题材、制作公司。区别于已有赛季的重点是短入口与即时结果。看完成率和次周回访率。 |
| 4 | 口味时间胶囊 | 想比较开播、中期、完结后自己的变化 | 利用 PersonalRun 和快照保存三个阶段，生成“升幅最大、跌幅最大、始终喜欢”对照图。不要修改旧快照。看二次测评率。 |
| 5 | 社区赛季结算与爆冷回顾 | 参与后想看投票有没有影响结局 | 在已有赛季基础上增加结束回顾、关键爆冷、争议对决和下一季提名；公示样本人数及票数规则。看结算页回访和下一季参与率。 |

先完成“能顺利进入 → 短时间得到结果 → 稳定分享 → 朋友能参与”的闭环，再扩大玩法数量。公共入口文案可减少 Manami、PNG 等实现名词，让用户先看到“选你看过的动画，做十次选择，生成榜单”。

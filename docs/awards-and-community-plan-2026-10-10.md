# AniMatch 颁奖礼与社区体验方案

日期：2026-10-10。状态：代码审查与线上只读检查后的设计方案，尚未实现或部署颁奖功能。下面的数字规则均为建议初值，需用本社区历史数据校验。

## 1. 当前发现与优先级

| 优先级 | 已观察到的现状 | 对用户的影响 | 建议 |
| --- | --- | --- | --- |
| P1 | `community-divergence.ts` 按等宽排名区间分 Tier，`community-tier-buckets.ts` 在标准五档中按 10%/30%/60%/85% 分界 | 例如 20 部有效作品的第 3 名，分歧解释中是 S，共享 Tier 图中是 A | 统一使用同一分档函数，说明这是相对排名档位，不是用户实际打出的档位；同分边界规则也应统一 |
| P1 | `TasteRivalryCard.tsx` 的个人请求失败被直接吞掉，`matches=null` 同时代表未登录、无记录、加载中和失败 | 已参与的用户可能看到“登录并参与后显示”，不知道实际是请求失败 | 拆分加载、匿名、无评价、无匹配、请求失败状态；失败提供重试 |
| P2 | 线上 7 月番组社区页在 1440×1000、滚动为 0 时，首条榜单结果位于 y=1074 | 首屏有行动区、说明、统计，却看不到榜单作品 | 切到社区页时缩为一行行动区；榜单优先；样本解释放指标旁；群友对照放桌面右栏或独立分页 |
| P2 | `ranking-evidence.ts` 将 3–9 人、至少 6 次比较、平均 Elo >1500 的作品视为小众发现 | 在不到 20 人的社区，固定人数不能表达作品是否小众 | 展示“4/15 人评价”，按本范围有效参与者的覆盖率识别低覆盖；不降低原有主榜排名来强行制造遗珠 |
| P2 | `PoolSeasonsSection.tsx` 将所有赛季直接铺成卡片 | 赛季越来越多时又变成长页面 | 默认展示进行中；未开始、已结束分组，历史赛季分页；保留当前赛季进度 |
| P2 | 榜单首层展示原始 Elo、社区分、离散度、轮次数、样本阈值等多种指标 | 用户要先理解算法，才能理解结果 | 首层用作品、名次、人数、直白结论；计算细节进入“为什么” |

检查范围：本地代码、线上未登录的公开番组社区页。没有模拟登录真实用户，也未修改线上数据；个人态问题来自代码路径审查。

## 2. 产品定位与页面结构

新增“本季颁奖礼”，从番组与赛季结果页进入。首页只放小型入口，不扩展全站顶栏。

颁奖活动必须绑定明确范围：一个番组的某次结算，或一个具体赛季；两个范围的评价、人数和投票不能混算。

```text
7 月新番 · 完结颁奖礼       提名中 / 投票中 / 已揭晓
参与 15 人   我的选择 6/10   待提名 2 项   揭晓 3/10
我的选择与社区一致：3/5 项（只统计双方都有结果的项目）

[概览] [作品] [角色] [制作] [音乐] [类型] [感受] [名场面] [结算]
[全部] [等我参与] [已选择] [已揭晓]        搜索奖项 / 候选

桌面：当前分类奖项卡片（两列）  | 待我参与、最近动态（窄侧栏）
手机：当前分类卡片（一列）；侧栏内容改独立入口
```

- 概览只展示 4–6 个精选奖项，加“等你参与”的一个明确行动。
- 每个分类默认显示最多 6 张卡，候选和理由进入抽屉或详情页。避免页面内再套大段滚动区。
- 分类导航桌面侧栏/顶栏二选一；手机可横向滚动，当前分类始终可见。
- 分类、筛选、奖项写入 URL；群里分享链接可以直接打开“最佳 OP”，返回保留原位置。
- 分类数量是奖项库结构，不等于每次活动必须启用所有奖项。默认精选 10 项，其余可添加。
- 顶部进度区区分“整个活动已揭晓”与“我已经选择”；弃权不计为漏做，不进入一致率分母。

### 卡片信息层级

```text
最佳 OP                         投票中 · 我已选择
当前领先：《歌曲名》—《所属作品》
我的选择：《另一个歌曲名》       [修改]
5/12 人选择 · 共 4 个候选
“目前只领先第二名 1 票。”
[投一票 / 修改选择 / 查看结果]   [候选与理由]
```

投票结束才显示“社区获奖”，活动中使用“当前领先”。自动统计奖显示“榜单推荐/结算结果”，主理人手动奖显示“主理人选择”。

每张卡不必同时出现参与人数、支持率、共识度、分歧度。指标随奖项变化，避免八项字段每次全部堆出。

## 3. 奖项库与推荐产生方式

| 大类 | 奖项 | 推荐产生方式 / 注意事项 |
| --- | --- | --- |
| 作品综合 | 最佳动画 | AUTO，沿用选定范围现有社区榜的合格第一名，避免颁奖页与榜单打架 |
| 作品综合 | 最佳单集 | NOMINATION_VOTE，候选是作品+集数+可选标题 |
| 作品综合 | 最佳动画电影、最佳短篇/特别篇 | TAG_AUTO，使用经过确认的作品类型 |
| 角色 | 最佳男主、男配、女主、女配、反派 | NOMINATION_VOTE，角色实体+所属作品+该奖项中的角色定位 |
| 角色 | 最佳 CP | NOMINATION_VOTE，两位角色的组合，统一顺序去重；默认只限本范围作品 |
| 制作 | 最佳监督、编剧、男声优、女声优 | NOMINATION_VOTE，人员实体+岗位+本次参评贡献；不可把作品 Elo 直接算成人员成绩 |
| 制作 | 最佳配乐 | NOMINATION_VOTE，作品配乐整体/OST；与单曲奖区分 |
| 音乐 | 最佳 OP、最佳 ED | NOMINATION_VOTE，歌曲/版本+作品；作品可有多个 OP/ED |
| 音乐 | 最佳动画音乐 | NOMINATION_VOTE，先约定插曲/主题曲等范围，是否允许 OP/ED 重复参评 |
| 来源与类型 | 原创、改编、续作、恋爱、喜剧、治愈、战斗、异世界 | TAG_AUTO 或 MIXED；确认候选标签后按同一社区榜选优；候选允许多分类 |
| 观众感受 | 最惊喜、最失望 | 首版 NOMINATION_VOTE；有同一用户前后期记录后增加“开播→完结变化”证据 |
| 观众感受 | 最想安利、最怪但我喜欢 | NOMINATION_VOTE，附一句可选理由 |
| 观众感受 | 最馊饭团、最金饭团 | 可自定义的社区奖；发布时必须有一句明确含义，不能默认为最低/最高 Elo |
| 演出作画 | 最佳作画片段、最佳演出回、最有记忆点场面 | NOMINATION_VOTE，作品+集数+可选时间段/外链；默认剧透遮挡 |
| 评选结算 | 最终冠军 | 没有额外决赛时与“最佳动画”合并；有决赛时取独立决赛票结果并注明 |
| 评选结算 | 最大分歧、最大共识、陪跑王、遗珠 | AUTO，但使用下面各自独立的证据规则，不只复用排行榜名次 |
| 评选结算 | 特立独行之选 | 个人分析 AUTO；每个人结果不同，不假装为统一社区冠军 |

### 五种类型在界面中的表达

- AUTO：根据已选数据范围生成，可查看计算依据；用户另填个人选择，不改变自动结果。
- TAG_AUTO：先明确候选资格；元数据未知不是“不符合”。允许补全标签并留下变更记录。
- NOMINATION_VOTE：提名→候选确定→投票→揭晓；普通用户可提名，无需管理员包办录入。
- MANUAL：主理人填写结果和理由，展示来源，不计入社区共识指标。
- MIXED：系统推荐候选，用户投票决定最终奖项；系统推荐与投票结果分别保留。不要偷偷调整 Elo 冒充投票修正。

## 4. 小群体的统计规则

### 4.1 共同约束

- 单个范围每人对每部作品只贡献一个有效评价。多个个人轮次、重复提名、多次投票请求都不能增加人数。
- 未看、未评价、隐藏的作品作为缺失，不填 0，也不解释成不喜欢。
- 现有自由排榜草稿不自动加入社区统计；需要有明确“提交本次评选”的动作与版本，避免重复计入同一用户的 Elo 和手排榜。
- 自动奖沿用现有数据资格；其统计范围、时间、算法版本必须可追溯。私心票的影响按该奖规则明确保留或排除。
- 不跨人、跨番组、跨季度直接相减原始 Elo。分歧类使用用户范围内的相对位置，并显示可比较作品数；这些指标仍是趣味统计，不是客观质量量表。
- 每种奖项保留自己的最低证据。小群建议 3 个有效参与者起进入投票结果，1–2 人可预览并提示“目前仅 2 人”；这不是统计可靠性的保证。
- 允许并列、空缺、弃权。没有足够证据时显示差哪项条件，不能强行产生一个冠军。

### 4.2 各奖的可解释规则

**最佳动画**：绑定现有社区榜排序及有效样本规则。截榜时保存完整排序、参与人数和来源版本。

**最大分歧**：不等于评分高，也不只看标准差。建议使用用户个人榜的归一化位置，至少有 2 人明显偏高、2 人明显偏低，优先寻找两极评价；卡片显示“3 人排在自己的前 20%，2 人排在后 20%”。不足时显示争议线索，不授予正式自动奖。个人只评很少作品时不能仅凭第一/末位就判两极。

**最大共识**：先区分“共同喜欢”和“意见接近”。奖项默认指共同喜欢：至少 3 位有效评价者，较高覆盖率、偏高评价占比大、分布集中。大家一致低分不能获得这个奖；可在详情叫“一致看法”，不要当成正面大奖。

**陪跑王**：用个人榜的前列次数和第一次数，显示“7 人排进前三，只有 1 人排第一”。只比较评价过足够作品的个人榜，建议至少 10 部；短榜改用前 20%，不能让只看 3 部的人每部都自动贡献一次前三。若指历史赛季屡次第二，应另建“赛季陪跑王”，不混用两种次数。

**遗珠**：低覆盖 + 至少少量强烈喜爱 + 未进入主要获奖/领先范围。示例候选条件：有效评价覆盖不高于 40%，至少 3 位评价者，其中至少 2 位在自己的充分评价榜中将其排进前 20%，且未进社区前三。这个定义允许作品整体好评但关注不足，不必人为认定它平均分低。2 人喜欢也可进“等待发掘”，不静默消失。

**特立独行之选**：比较我的位置与其他用户的位置分布，社区参考中剔除我自己。显示“你排第 2，另外 6 位评价者多数排在中下游”，不能把我的评价同时放进对照基线。

**惊喜 / 失望**：首版用户直接选择并填写可选理由。后续同一用户对同一作品的开播预期与完结评价才能配对；同分级量表更容易解释。只有前后期相对排名时称“口碑上升/下降”，不能直接等同主观惊喜/失望。仅看完结低分无法知道这个人是否曾抱有期待。

### 4.3 百分比与热区文案

- 投票奖用“5/12 人选择”，可附 42% 支持率。分母是该奖实际有效投票者，不是整个网站注册用户。
- 排名奖用“8 人评价，6 人排在前列”；不要把 Elo 或标准差直接换成“共识 72%”。
- “一致率”仅统计我有明确选择、社区已结算且可比较的奖项；并列获奖中包含我的选择则算一致；显示 3/5，零项时显示暂不可比。
- 不同奖项的分歧指标不强行比较成同一百分数。
- “你比 86% 的人更喜欢”必须有明确他人评价集合、并列规则和缺失处理。第一版优先用“你比 6 位已评价者中的 5 位排得更高”。
- 热区文案根据真实事实使用模板。例如领先 1 票才写“只差一票”，高低两派都存在才写“最吵的一桌”。不虚构群友原话。

## 5. 候选数据不能只靠一段文本

面向用户：搜索已有候选；没有则“补充提名”。界面按类型只显示必要字段，后台统一为结构化候选。

| 类型 | 必要标识 | 可选展示资料 |
| --- | --- | --- |
| 动画 | animeId | 现有封面、别名 |
| 单集/演出回 | animeId + 集数或特别篇标识 | 集名、剧透级别 |
| 角色 | 角色 ID 或临时实体 ID + 关联作品 | 名称、头像、别名；候选定位单独记录 |
| CP | 两个角色 ID 的规范组合 | CP 名、关联作品 |
| 人员 | 人员 ID 或临时实体 ID + 参评岗位 | 本范围内的贡献作品/角色列表 |
| OP/ED/歌曲 | 作品 + 歌曲实体/临时 ID + 版本/用途 | 歌手、外链、封面 |
| 片段/场面 | 作品 + 集数 + 时间范围或场面标识 | 一句话介绍、外链、剧透标记 |
| 自由文本 | 临时候选 ID + 名称 | 关联作品、候选种类待补全 |

纯文本允许先提名，不要求一次建立完备角色百科。展示时明确“信息待补全”；实体 ID 优先去重，文本归一化只用于提示疑似重复，不自动合并同名角色。

管理员合并重复候选必须保留原 ID 映射和记录；同一个用户投给两条重复记录不能合并成两票。结算后纠错发布新版本，不覆盖历史。

封面继续使用现有 AnimeCover 与图片缓存；候选图缺失时有有意义的文本卡。OP/ED 第一版提供外链，不默认自动播放；剧透图片与内容揭示由用户主动打开。

## 6. 投票、社区互动与活动生命周期

```text
草稿 → 提名中 → 候选确定 / 投票中 → 截止结算 → 揭晓
```

- 第一版每个投票奖每人一票，截止前可以改选或撤回，支持跳过。候选太多时明确两轮投票，不临时改变计票方式。
- 提名期每人每奖可补充 2 个候选为建议初值；重复候选改为支持已有提名。别把提名数等同最终票数。
- 投票阶段新增候选需公开重新开提名或安排下一轮，避免最后一分钟加候选引发公平性争议。
- 截止时间由服务端判定；截止与最后一票需要事务保护。结算幂等，保存结果快照、人数、候选、规则版本和并列。
- 建议普通奖公开实时进度、投票后看当前票数；主奖可选截止后统一揭晓。活动发布时固定规则。
- 主理人可以办“揭晓模式”：全屏逐个开卡、显示获奖理由、导出整届奖单，适合群聊共同看。
- 理由可点赞或“同感”，但互动数不混入投票成绩。理由应可删除/举报，并有长度、频率限制。
- 名场面支持剧透遮挡；个人比较文案围绕作品差异，避免把玩法变成针对用户的负面评价。

### 三个优先社区闭环

1. **给提名拉票**：提名 → 一句理由 → 分享该奖 → 群友投票 → 揭晓后理由进入获奖卡。
2. **遗珠补番**：发现遗珠 → 加入“想看” → 看后补充评价 → 看到自己的评价如何改变下一次结果。冻结的旧结果不变。
3. **开播押宝到完结回看**：开播选择期待作品 → 完结填写惊喜/失望 → 生成个人对照卡。默认娱乐预测，不影响作品 Elo。

## 7. 年度整合

- 四季度的获奖、提名与结果快照作为年度候选来源；同一作品、角色、人员、歌曲以实体 ID 去重。
- 每季度推荐固定数量候选，额外留“年度补提名”位置，让没有进季度榜的作品仍有机会。
- 季度投票人数不作为年度票数累加；年度重新投票或建立新的年度对决，避免夏季人多就天然胜出。
- 同一人同一作品跨季度重复评价，年度统计按已公布的取值规则去重，例如年度截止前最近一次完结评价。
- 年度页同时区分“全年获奖记录”与“年度最终获奖”。最佳监督候选可汇总全年多部作品贡献。
- 当前已有 AnimeCollection/CollectionSource/BattleSeasonArchive 可作为季度来源和冻结数据基础；新增奖项快照，不能假设已有赛季快照已包含角色和奖项信息。

## 8. 技术落地与边界

建议新建独立的 awards 模块，不继续向已经很大的番组 page.tsx 中堆业务。

- AwardEvent：poolId、可选 seasonId、标题、状态、时间、范围版本、展示配置。
- AwardDefinition：奖项库代码、大类、中文名、候选类型、默认规则。
- EventAward：活动内启用的奖项、产生方式、规则配置、状态。
- AwardCandidate：候选实体类型、名称、规范标识、展示资料；关联作品用关联表，允许人员有多部贡献。
- AwardNomination：候选与奖项的关联、提名人、理由；同奖同候选唯一。
- AwardBallot：userId + eventAwardId 唯一，候选 ID、更新时间/版本；数据库或事务校验候选属于同奖。
- AwardResult：结算版本、获奖者（允许多个）、完整统计快照、数据截止时间、算法版本。
- AwardReaction / AwardComment：第二阶段再上；避免第一版一口气引入完整社交系统。

API 建议：`/api/pools/:poolId/awards`、`/api/award-events/:eventId`、`/api/event-awards/:awardId/nominations`、`/ballot`、`/results`。所有读写继承番组访问权限；创建/结算检查创建者或管理权限；提名与投票使用登录用户身份。

列表只返回卡片摘要，候选按奖加载。图片用缩略图，详情按需加载。用户投票独立事务，统计批量聚合或短时缓存；改票后刷新对应卡片。不要每次打开卡片重新查询全站全部评分。

### 上线验收重点

- 一人多轮、重复提交、并发改票不能增加票数或人数；跨奖候选不能被投票。
- 私有番组不可通过 awardId 泄漏；管理员动作与普通参与动作区分。
- 未看不计低分；同分与并列稳定；样本少时有明确说明；个人一致率分母可解释。
- 截止边界、重复结算、历史快照、季度去重有真实案例测试。
- 手机无横向溢出；一次只读当前分类；抽屉键盘可操作并能返回焦点；导出有封面加载失败回退。

## 9. 分阶段交付

1. **先统一现有体验与数据口径**：统一社区分档、修正个人匹配加载状态、榜单首屏压缩、赛季归档分组。
2. **最小颁奖礼**：完整提名→投票→揭晓流程；默认 10 项：最佳动画、最大分歧、遗珠、陪跑王（自动分析）+最佳角色、最佳 CP、最佳 OP、最佳单集、最惊喜、最失望（提名投票）。主持人可选男女主等细分模板替换最佳角色。低样本自动奖允许空缺。
3. **增强群聊参与**：提名理由、精准分享、结果卡、逐项揭晓、名场面剧透遮挡、制作人员与细分类奖项。
4. **年度回顾**：季度获奖候选汇总、年度新一轮投票/对决、开播完结对照与个人年度奖单。

每一步交付能独立使用的闭环。奖项库可以完整保留，但界面默认只启动有参与基础的奖项。

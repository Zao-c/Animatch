# AniMatch 公开发布准备

本清单用于将 AniMatch 从好友群内部使用整理为面向公开访问的项目页面及部署版本。它记录需要人工确认的发布事项，保留现有业务流程和数据。

## 1. 发布前技术核对

- [ ] 确定准备发布的代码分支与提交 SHA，明确各个未合并 PR 的依赖与验收顺序
- [ ] 检查 GitHub Actions：Prisma Client、TypeScript、单元测试及 Next.js 生产构建
- [ ] 在预发布环境完成桌面与手机实测：登录、公开番组、动画对决、Tier List、公开音乐曲单、试听、个人曲单、分享链接
- [ ] 为每套环境配置独立的 `AUTH_SECRET`、数据库密码、邀请码和第三方服务密钥
- [ ] 将现有好友群**共用密码登录模式**升级为适合公开用户的独立账号认证；验证密码重置、账号隔离、注册频率限制及权限边界
- [ ] 复查公开仓库中的历史日志、服务器地址、测试账号、示例环境文件和图片元数据，确认其对公开发布的适用性
- [ ] 在升级前备份生产数据库、用户上传封面与音频，以及相应对象存储数据
- [ ] 依据既有迁移历史验证升级路径，生产环境遵循 [部署指南](deploy-server.md)；`prisma db push` 专用于全新本地数据库
- [ ] 核对公开曲单中使用的音频、封面、iTunes 等第三方来源的实际使用条件，保留权利说明

## 2. README 截图重新制作

以前的 `docs/images/*.png` 和各个 `docs/anisong-*/` 目录主要用于开发验收、历史对照。它们继续保留在文档目录中；公开首页建议只展示**从拟发布版本直接采集的真实界面**。

推荐拍摄以下四张，信息量按读者认识产品的顺序排列：

| 文件名建议 | 画面 | 核心信息 |
| --- | --- | --- |
| `docs/images/release/home.webp` | 首页或公开番组大厅 | AniMatch 是动画与音乐对决网站 |
| `docs/images/release/anime-match.webp` | 两部动画封面并排、选择操作清晰的对决页 | 两两对决如何操作 |
| `docs/images/release/tier-list.webp` | 已生成、封面完整的动画 Tier List | 对决的实际结果 |
| `docs/images/release/music.webp` | 公共音乐曲单详情或音乐对决 | OP / ED 音乐玩法 |

**取景标准**

- 桌面截图优先使用统一的 **1440 × 900** 浏览器视口；另拍 **390 × 844** 手机版核对文字、按钮和滚动
- 在真实页面完成数据加载后拍摄；保持一致的主题、页面缩放与浏览器状态
- 使用获得许可的展示素材、公开数据或独立演示账号，避开个人账号资料、私人音乐文件、认证信息与调试提示
- 尽量让封面、对决按钮、Tier 档位成为画面主体；把菜单、系统通知与无关空白移开
- 优先导出宽度约 **1200–1440px** 的 WebP，质量约 80–88，尽量把单张图控制在数百 KB；按实际视觉质量调整
- 文档图片应附简洁准确的替代文字，并标注这是一张实际页面截图
- 确认每张画面都来自准备公开的同一提交，不使用效果图冒充真实页面
- 正式展示图通过浏览器验收后，再添加到根目录 README；历史截图继续作为研发证据保留

## 3. GitHub 仓库呈现

- [ ] 根目录突出 `README.md`、`LICENSE`、`Dockerfile`、部署与构建配置
- [ ] 早期 Word 方案、实验提案、旧截图与验证产物保存在 `docs/` 或其归档目录
- [ ] 设置仓库 About 描述、Topics、主页网址（确认实际可访问后填写）
- [ ] 在 README 第一屏解释产品做什么，再给出使用流程、技术栈与部署方式
- [ ] 按当前实际功能整理发行说明与版本号，完成移动端截图和许可审查
- [ ] 检查文件大小与历史记录：普通移动或删除只整理当前树，Git 历史仍保留以往的大文件；是否需要专项历史清理应单独评估，并保护现有 PR 与协作者

## 4. 发布后验收

- [ ] 首页、公开入口及静态资源访问正常
- [ ] 新账号只能访问自己的私人历史、草稿及上传记录
- [ ] 匿名访客只能查看符合公开规则的内容
- [ ] 分享快照及撤销分享流程在移动端与桌面均正常
- [ ] 数据库备份能在隔离环境恢复，且回退流程已经演练

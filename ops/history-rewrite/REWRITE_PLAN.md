**Git Tree 一致**指 Git 跟踪内容一致，含文件路径、内容、可执行权限及符号链接。Commit SHA、作者时间、合并关系和按提交粒度的溯源信息发生变化。GitHub Compare 可能显示大量差异，源于两条分支仅共享最早的根 Commit；应以 Tree SHA 或 `git diff --exit-code` 判断实际内容差异。

完整旧历史由备份分支继续引用；精简提交的消息中保留原始里程碑 SHA。

## 服务器部署和运行中数据

仓库 `docs/deploy-server.md` 包含 `git pull` 升级流程，`docker-compose.prod.yml` 运行 Next.js 与 PostgreSQL，还有用户上传封面与音频、第三方对象存储相关配置。

服务器 AI 必须实际检查：

1. 正在运行的代码目录与 `git rev-parse HEAD`、分支、远程、工作区未提交修改和 `git worktree list`；
2. Compose / systemd / PM2 的真实部署方式、容器健康、构建产物与是否硬编码提交 SHA；
3. PostgreSQL 数据目录、数据库备份和恢复演练；
4. 用户上传音频/封面持久化目录、云对象存储桶、访问控制及备份；
5. 生产服务的访问地址、监控和发布窗口；敏感信息一律脱敏后汇报。

历史切换以后，旧服务器工作区继续沿用旧祖先，直接 `git pull` 可能触发分支分歧提示。推荐在独立目录检出新版本、完成依赖/构建与健康检查，再根据维护窗口做原子切换；保留旧目录便于回退。如采用原目录，先备份数据及工作区，确认所有本地修改已妥善保存，再按经审核的新 SHA 显式重建工作区。

**精简 Git 历史不会替代数据库、音频或封面备份。** 单纯 Git Tree 相同通常意味着此次历史精简本身不会引入新 schema；如果期间合并功能 PR，仍需对照迁移文件和部署手册验收。

## 执行流程

### 阶段 A：当前可以完成

1. 再次核对远程 `main`、`backup` 和 `preview` 的 SHA/Tree；检查 3 个 Open PR。
2. 在有足够存储空间的环境运行 [preflight_and_full_backup.sh](preflight_and_full_backup.sh)，获得 Git Mirror、经过 `git bundle verify` 的离线 Bundle、`.sha256`、全部 Git refs 和提交清单。
3. 独立测试环境 checkout `preview/main-release-milestones-20261123`，使用 Node 20 与 pnpm 9.15.0，运行：
   - `pnpm install --frozen-lockfile`
   - `pnpm exec prisma generate`
   - `pnpm exec tsc --noEmit`
   - `pnpm test`
   - `pnpm build`
4. 在预发布数据库完成登录、角色权限、动画对决、音乐曲单、旧记录、Tier、公开分享和撤销分享的真实测试。
5. 规划 #1/#23/#33 的移植和生产工作区迁移；必要时在独立分支提交 PR 供审核。
6. 生成脱敏报告，标明 SHA、备份 Bundle SHA256、测试结果、冲突、剩余风险及需用户批准的事项。

**CI 说明：** `.github/workflows/ci.yml` 仅在 PR 和 `main` 推送时自动触发。当前 `preview` 尚未有单独的自动 CI 结论；必须通过本地或独立环境执行测试，记录结果后再申请切换。

### 阶段 B：仅在仓库所有者单独批准后开展

1. 确认主分支冻结，所有 PR、生产部署版本、历史备份和离线 Bundle 均已经核对。
2. 若现有 `main` 有任何新提交，重新取快照并更新预览，要求 **新预览最终 Tree 与计划替换时 `main` 的 Tree 完全一致**。
3. 使用完整 SHA 与精确期望值进行 **force-with-lease**，仅替换 `refs/heads/main` 一次；在 SHA 已变化时终止并重新规划。
4. 触发新的 `main` CI，完成预发布及正式环境验收，更新服务器的 Git 工作区和部署引用。
5. 持续保留原始完整历史分支和离线 Bundle；再按实际合并记录清理旧分支。

**重要：本任务书下发时只执行阶段 A；阶段 B 必须由所有者另行明确授权。**

## 回退路线（批准后的应急计划）

远程历史备份指向原始 `68aee4df118acb8d4c3e97966f05d5f70a23c33c`。若新 `main` 上线后出现问题，先记录其实际新 SHA，在所有者审批后使用该 SHA 作为 `--force-with-lease` 的预期旧值恢复原始 `main`。同时核对服务器工作区、Docker 镜像和数据库/音频备份，验证 CI 与业务健康后才认定回退完成。

任何历史重写都影响旧 Git `blame`、`bisect`、PR 提交定位及合并基线，因此需要长期保留原备份。

## 仓库体积与历史保留的区别

精简 Commit 改善可阅读性；只要远程完整历史备份保留，GitHub 仍需保留旧对象，仓库体积与克隆体积不会立即同比缩小。项目历史审计、精细化回退和事故排查仍以 `backup/main-full-history-20261123` 为依据。
